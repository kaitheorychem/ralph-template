# 規約

Ralph ループのイテレーションに限らず、このリポジトリで研究作業をするすべてのセッションが従う。パスはリポジトリルートからの相対。運用の設定値（ベースブランチ・マージ方針・1日の上限）は [ralph/config.env](config.env) にある。

## 誠実さ（最優先）

理論研究の自動化でいちばん起きやすい失敗は「検証したふり」と「合わせ込み」である。以下は例外なく守る。

- 式変形を「明らかに」「同様に」「整合性から」「〜となる」で飛ばさない。計算を示すか、「分からない」「未確認」と書く。
- 数値や図を合わせるために、係数・パラメータ・項・許容誤差を調整しない。不一致はそれ自体が発見なので、記録して原因を調べる。
- 「検証済み」「一致した」と書くのは、実行したコマンドとその結果を示せるときだけ。
- 既存の検算を消す・弱める・飛ばすことはしない。変える必要があれば理由を書いて QUESTIONS.md で人間に諮る。
- 別の系・別の文献の結果を流用するときは、前提（次元・境界条件・規格化・符号の約束・近似の範囲）の違いを列挙して確かめる。
- 誤りを1つ見つけても点検を打ち切らない。新しい問題が出なくなるまで続ける。
- 文献の書誌（著者・題名・雑誌・年）は refs/ の原典か取得したページで確かめる。記憶から書くなら「要確認」と付ける。
- 人間の意向を推測して結論を寄せない。根拠の無い結論より「未解決」のほうがよい。

## 作業単位

- 1イテレーション = 1タスク。大きいタスクは PLAN.md 上で分割してから着手する。迷ったら小さい方を選ぶ。
- 人間の判断が必要な事項（理論の方向転換、既存結果と矛盾する発見、先行研究の解釈が分かれる点、GOAL や規約の変更提案など）は勝手に決めず、`ralph/QUESTIONS.md` に書いて別のタスクに移る。

## 配置と命名

| パス | 内容 |
|---|---|
| `theory/NN-topic_name/` | 確定した理論。連番2桁＋英小文字とアンダースコア（例 `theory/00-basic_model/`）。書きかけを残さない（TODO・FIXME・WIP は lint が止める） |
| `theory/CONVENTIONS.md` | リポジトリ全体の単位・符号・記号の約束。追記してよいが、既存の約束の変更は QUESTIONS.md で諮る |
| `idea/` | 下書き・途中計算・没案。本文化して役目を終えたメモは削除してよい |
| `refs/` | 人間が置く先行研究。書き換えない。要約ノートだけは `refs/notes/<key>.md` に置いてよい |
| `tools/NN-topic_name/` | 数値検算（theory と同じトピック名） |

- 完成済みのトピックは原則書き換えない（新トピックへのリンク追記などの軽微なものを除く）。
- **人間が管理するファイル**（エージェントは変更しない。lint が検出する）：AGENTS.md、CLAUDE.md、README.md、ralph/{PROMPT,RULES,GOAL,README}.md、ralph/config.env、ralph/loop.sh、ralph/bin/、ralph/ci/、.claude/、.github/、tools/check_all.sh、refs/（refs/notes/ を除く）。変えたほうがよいと思ったら QUESTIONS.md で提案する。
- ralph/ でエージェントが書くもの：PLAN.md、QUESTIONS.md（質問の追記と「反映済み」の付記）、NOTES.md、claims.json、journal/ と reviews/（新しいファイルの追加のみ）。

## 執筆スタイル

- 各トピック直下に README.md（概要・ファイル一覧・記号表・要点・主張 ID との対応）を置き、個別の内容は独立した .md に分ける。
- 数式は LaTeX（`$...$`、`$$...$$`）。後から参照する式には番号を付ける（例：`(2.3)`）。
- 文体は「だ・である」調の簡潔な説明文。
- 記号は CONVENTIONS.md とトピックの記号表に従う。教科書の慣習に戻さない。新しい記号は初出で定義し、記号表にも載せる。既存の記号と衝突させない。
- 結論には導出を付ける。長い導出はファイルを分け、README から流れが追えるようにする。
- 先行研究と重なる結果には出典を明記し、何が既知で何が新規かを区別する。

## 検証

- 閉じた式を出したら、具体的な数値例を最低1つ入れて検算する。
- GOAL.md「検証の基準」に挙げた極限・特殊ケース・参照値・整合チェックのうち関係するものを確かめ、本文にも明記する。
- 検算は**理論の式を使わない独立な基準**（直接計算・数値積分・数値対角化・別の方法・文献値）と突き合わせる。理論の式を書き写して自分自身と比べるだけのものは検算ではない。
- 乱数はシード付きで再現可能にする。許容誤差は根拠（数値誤差の見積もり）を添えて決める。
- 結論の根拠になった検算は使い捨てにせず `tools/<topic>/` に残す。単発の手計算で再利用の見込みが無いものまで残さなくてよい（迷ったら残す）。
- 各 `tools/<topic>/` に置くもの：
  - `check.sh`：そのトピックの検算を全部走らせ、全部合えば終了コード 0、1つでも外れれば非 0。出力は短く（1検査1行程度、詳細はファイルへ）。重い検算は `CHECK_FAST=1` のとき縮小版で走らせてよい（完了判定と CI はフル）。
  - `README.md`：各検査がどの理論ファイル・主張 ID に対応するかの表。
- `check.sh` の最小形（各 `check_*.py` は `PASS 名前` か `FAIL 名前: 理由` を1行出し、外れたら非 0 で終わる）：

```bash
#!/usr/bin/env bash
cd "$(dirname "$0")" || exit 1
fail=0
for t in check_*.py; do python3 "$t" || fail=1; done
exit $fail
```

- 全トピックの検算は `tools/check_all.sh`（`tools/check_all.sh <topic>` で1トピック）。コミット前に必ず走らせる。
- 検算に要る Python パッケージは requirements.txt に書く（クラウドではセッション開始時に入る）。

## 査読

- `theory/` に結果を足した・直したときは、書いた本人とは別の文脈で査読する。Claude Code では referee サブエージェント（.claude/agents/referee.md）に依頼する。依頼文の型：
  > referee として次を査読してほしい。対象：<ファイル>（主張 <ID>）。差分：origin/main との差分。基準：GOAL.md の <問い>、theory/CONVENTIONS.md、<トピック> の記号表。検算：tools/check_all.sh <topic>
- レポートは `ralph/reviews/NNNN-<短い名前>.md` に保存する。referee の返答をそのまま貼り、`判定: PASS` か `判定: NEEDS_WORK` の行を必ず入れる。再査読したら同じファイルに追記する（最後の「判定:」行が最終判定として扱われる）。
- 直すのは正しさと GOAL の要件に関わる指摘。文体の好みは任意。
- 完了監査（PROMPT.md 手順2）では差分ではなくトピック全体を通読させる。

## 主張台帳（ralph/claims.json）

- GOAL.md の問いに答える主要な結果（式・定理・数値的結論）を1件1主張で登録する。補題まですべて載せる必要はない。
- 項目：`id`（C1, C2, …）、`question`（Q1 など）、`statement`（一文）、`location`（theory 内のファイル。`#` 以降に式番号などを書いてよい）、`check`（検算の場所 tools/…）、`status`、`review`（査読レポート）、`note`（任意）。
- `status`：
  - `draft`：まだ検証が済んでいない（計画段階の枠もここ。`location` はこれから書くファイルでよい）
  - `checked`：検算と極限チェックが `check` で走り、通っている
  - `refereed`：さらに referee の `判定: PASS` が `review` にある
  - `refuted`：誤りと分かった（理由を `note` に書く）
- 主張は削除しない。条件を満たさないのに `status` を上げない（lint が検出する）。内容を直したら `status` を下げて検証し直す。

## NOTES.md

- 次の自分への申し送り。journal（時系列の記録）から、繰り返し効く知見だけを蒸留して書く：試して駄目だったやり方とその理由、記号・数値の落とし穴、検算のコツ。
- 1項目1〜2行、全体 100 行以内。古くなった項目は消すかまとめる。

## journal

- 1イテレーション = `ralph/journal/` の1ファイル。既存のファイルは書き換えない（誤りは次のエントリで訂正する）。
- ファイル名：`NNNN-YYYY-MM-DD.md`（NNNN は既存の最大番号 + 1、4桁ゼロ埋め。日付は `date +%F`）。
- 各項目3行以内、全体 20 行以内。詳細は theory / idea / tools / reviews に書いてリンクする。
- 書式（preflight の WARN があれば最後に「警告:」の行を足す）：

```markdown
# イテレーションN：タスクの短い名前（YYYY-MM-DD）

- やったこと:
- 結果・分かったこと:
- 検証: 実行したコマンドと結果（例：tools/check_all.sh → 全 PASS）
- 査読: PASS / NEEDS_WORK / なし（ralph/reviews/NNNN-….md）
- 次にやるべきこと:
- 未解決の疑問:
```

## Git

- コミットメッセージ：理論本体 → `theory/<番号>: <やったこと>`、検算 → `tools: <やったこと>`、ループ運用ファイル（PLAN・QUESTIONS・NOTES・claims・journal・reviews）だけ → `ralph: <やったこと>`。
- 動く状態・読める状態でコミットする。`tools/check_all.sh` が FAIL のままコミットしない（直せなければ原因の変更を idea/ に退避する）。
- PR のタイトルは `[ralph] ` で始める（未マージ PR の検出に使う）。ベースは config.env の `RALPH_BASE`。本文には、やったこと・検証コマンドと結果・査読の判定・人間に見てほしい点を書く。
- マージは config.env の `RALPH_MERGE` に従う：
  - `human`：PR を作って終わる。マージは人間が行う。
  - `auto`：PR を作ったら自動マージを有効にする（GitHub のツール、またはクラウド環境なら REST の `PUT /repos/{owner}/{repo}/pulls/{n}/ccr/auto_merge`）。有効にできなければ人間に任せ、その旨を PR 本文に書く。

## 対話セッションからの引き継ぎ

人間と対話しながら研究を進めたセッションも、終える前にループが続きを拾えるようにする（Claude Code では `/ralph-handoff`）：PLAN.md と claims.json の更新、journal の新規エントリ（見出しに「（対話）」と付ける）、必要なら NOTES.md。
